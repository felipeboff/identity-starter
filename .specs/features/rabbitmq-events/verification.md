## Findings

None of these makes a check fail: each check's claim, as written, has a located assertion that settles it. They are ranked by how much behaviour they leave unproven.

1. **The plan's S3 independent test, and AC 20's "declare the topology again", are only partly proven (C23: level and sampling).**
   - What the plan asks (`plan.md:140-141`): with the API running, restart the RabbitMQ container, then a sign-up reaches a test subscriber's queue.
   - What C23 does: it runs at integration level, without `start`. The management API drops the suite user's connections and the same broker keeps its queues (`rabbit-message-consumers.integration.spec.ts:114-118`, `rabbitmq-broker.ts:63-64`).
   - The exchange and the durable or quorum queues outlive the drop. A reconnect that skipped re-declaring the topology would therefore still pass C23.
   - Re-declaration is visible only in the code: the channel `setup` re-runs `open()` on every reconnect (`rabbit-message-consumers.ts:50`, `:77-99`).
   - No test runs the API through a broker drop or restart.
2. **C7's "resolves once the broker confirms" is configuration, not an assertion.**
   - The test awaits `send` and then polls for the message (`rabbit-event-broker.integration.spec.ts:72-74`). A fire-and-forget channel would pass it too.
   - C8's broker-away proof (`:146`) rejects through the publish timeout. That timeout also applies when no channel ever connected, confirm or not.
   - The guarantee rests on `confirm: true` (`rabbit-event-broker.ts:32`) and on the library resolving in the confirm callback (`ChannelWrapper.js:400-414`).
   - AC 6's "only after the broker's confirmation" is therefore proven on the relay side (C6, C8) and read from the code on the broker side.
3. **C6's "only after it resolves" needs C8.** `seen` is captured when `send` is called (`outbox-relay.spec.ts:107-110`), not after it resolves. A relay that called `send` without awaiting it and then ran `markProcessed` would still pass `:116-125`. C8's `:230-232` catches that relay: a rejected `send` leaves the entry unprocessed.
4. **C22's ordering assertion cannot catch a skipped relay stop.**
   - `start.e2e.spec.ts:605-608` sorts a spy that was never called as `(first ?? 0)`, so it lands first. If `stop` skipped `OutboxRelay.stop`, `"relay"` would still be first and `:609-618` would pass.
   - Every other step would jump ahead of `"relay"` if skipped, so those are caught.
   - The relay leg rests on "starts the outbox relay after listening and stops it before closing the database" (`start.e2e.spec.ts:646`, `expect(closesWhenRelayStopped).toBe(0)`). That test passed in the full `pnpm test:coverage` run but is not a named proof. The same pattern was flagged in the `bullmq-jobs` report.
5. **C12's binding and `handler.name` legs are proven by other tests.**
   - C12's assertions (`rabbit-message-consumers.integration.spec.ts:130-151`) check that the exchange, the dead-letter queue and the quorum queues exist. They check no binding.
   - The binding to the event name shows only through routing in C13 (`:182-190`) and C14 (`:218-229`).
   - Queue name = `<APP_NAME>.<handler.name>` comes from `MessageConsumerAdapter.toSubscriptions` (`message-consumer-adapter.ts:21`). It is asserted by "subscribes each consumer to its event under its handler's name" (`message-consumer-adapter.spec.ts:47-55`), which no check names.
6. **Inbox 7-day retention: no check proves it (Swept and door 5).**
   - C20's contract uses an arbitrary `expiresAt` (`inbox.contract.ts:19`, `faker.date.soon`). Its Mongo test asserts only a TTL index with `expireAfterSeconds: 0` (`mongo-inbox.integration.spec.ts:56-62`).
   - The 7-day value (`message-runner.ts:10`) is asserted only at `message-runner.spec.ts:64-71`, in "hands the payload to the handler with the event id and keeps the inbox entry". That test passed, but no check names it.
7. **Door 2's event name format is not enforced per kind.** `outbox.schema.ts:4` accepts two or three dotted parts for both kinds. An event named `<module>.<effect>`, or an effect with three parts, is stored. C27 proves only that a one-word type is refused (`mongo-outbox.integration.spec.ts:140`). Door 10 makes `kind` explicit and refuses to infer it from the format, so this is a precision gap against door 2's wording, not a contradiction.
8. **An unsettled delivery can wait a long time (not in any check; the "subscriber outcomes (5)" set leaves it out).**
   - When the retry or dead-letter republish, or the `ack`, throws, `settle` logs `shared.message_unsettled` and leaves the message unacknowledged on a live channel (`rabbit-message-consumers.ts:131-138`).
   - The message holds one of the 10 prefetch slots (`:65`) until the channel closes: a reconnect, or the broker's consumer acknowledgement timeout.
   - The unnamed test at `:434-467` forces a connection drop to show redelivery. Nothing bounds the wait in production.
9. **A Mongo blip dead-letters events whose handler never ran (risk).**
   - `MessageRunner.run` treats any error from `transactions.run` as a handler failure (`message-runner.ts:41-45`), including a failed inbox write or transaction commit.
   - Retries come milliseconds apart (accepted in the plan's Out of scope), so a database blip of a few milliseconds can use up all 5 attempts and send the event to `<APP_NAME>.dead`.
10. **Retry is "republish, then ack", not atomic (risk, low).** `rabbit-message-consumers.ts:128-130`: a crash or a closed channel between the `sendToQueue` copy (attempt n+1) and the `ack` leaves both the copy and the original in the queue. A failing message can then run more than 5 times and be dead-lettered twice. The inbox absorbs only successful runs.
11. **Other risks seen while reading (low).**
    - Nothing stops two `MessageConsumer`s sharing a `handler.name`. They would share one queue, bound to both events and consumed twice. Handler names are module-prefixed (e.g. `identity.sign_out`), so collisions across modules are unlikely.
    - In `start`, a failure in `subscribers.start()` or `events.ready()` after `listen` (`start.ts:196`, `:204`) closes nothing, the same as the existing `scheduledJobs.sync()`. `events.ready()` waits for a connection with no timeout of its own.
12. **Documentation drift (outside the checks).**
    - `docs/adr/001-transport-neutral-handler-layer.md:61` still declares `MessageConsumer = Entry & { queue }` and "anything else: nack / retry". Door 4 replaced both. ADR-013 says it "applies" ADR-001 (`:89`) but does not mark that row superseded.
    - ADR-013 cites "Landing doors 1-9" (`:90`), but door 10 exists.
    - The integration and e2e setup uses `rabbitmq:4-management` (`rabbitmq.global-setup.ts:15`), not door 7's `rabbitmq:4`. The management API is needed for per-suite broker users and for dropping connections; the Handoff "Abandoned" row implies this but does not state it.
