## Findings

None of these fails a check. They are ranked by how much they weaken a claim's evidence.

1. **Precision: three literal names are asserted only through the constant that defines them (C9, C10, C16).**
   - **What the tests compare.** The tests compare against `NotificationsLogEvent.EmailDeliveryFailed.name` and `NotificationsOutboxEffect.EMAIL_CHANGED_NOTICE`. The literals the checks name live at `src/modules/notifications/infrastructure/notifications.log-event.ts:16` (`"notifications.email_delivery_failed"`) and `src/modules/notifications/application/outbox/notifications-outbox-effect.ts:3` (`"notifications.email_changed_notice"`).
   - **What no test pins.** `rg` over `*.spec.ts` finds no assertion on either literal, so a typo in the constant would stay green.
   - **How the other names are covered.** `notifications.email_logged` is pinned at `start.e2e.spec.ts:104` and `notifications.welcome_email` at `start.e2e.spec.ts:544`.
   - **What the checks say.** `checks.md:96` says "each has a proof that asserts that value". For these two, that is true only through the constant. I confirmed both values by reading the code.
2. **Precision: C3's "same Mongo transaction" is shown only indirectly.**
   - **What the assertion shows.** `notifications.module.integration.spec.ts:192` (`running` = `[true]`) shows a transaction is open when the effect is published. That would also hold if the use case's own `transactions.run` opened a separate transaction.
   - **What actually proves the join.** The join itself rests on `src/shared/infrastructure/mongo/mongo-transaction-runner.ts:16`, the shared code from rabbitmq-events, and on C1's in-memory abort test (`schedule-welcome-email.use-case.spec.ts:55-66`).
   - **What is missing.** No integration test aborts the inbox's Mongo transaction after the effect is written to show that both vanish.
3. **Precision: C17 proves one `FetchHttpClient` instance, not one `MailSender`.**
   - **The gap.** Two `MailerSendMailSender`s built over a shared client would pass `start.e2e.spec.ts:664`. The Handoff records this as a deliberate choice: `src/app` may not import a module's infrastructure.
   - **What settles it.** Reading the assembly settles the claim: `start.ts:124-135` and `notifications.module.ts:52-79`.
4. **Level: C14's route half rests on tests the feature did not touch.**
   - **What the route tests stub.** `invitations.e2e.spec.ts:217-233` and `email-change.e2e.spec.ts:75-87` stub `http.ctx.mailer` (the `IdentityMailer`) with an `AppError`. They prove the existing route mapping ("as today", AC 12), not the new `MailSender` path.
   - **Where the new link is proven.** The new link (`MailSender` rejection to `identity.email_delivery_failed`) is proven only at integration level, and only through `sendInvitation` (`composing-identity-mailer.integration.spec.ts:64`). `sendEmailChange` uses the same private `send` (`composing-identity-mailer.ts:41-47`).
   - **Handoff.** The Handoff (`checks.md:113`) lists both e2e specs and the identity-http helper among "existing files touched". All three are unmodified in the working tree.
5. **Not covered by any check: the notice's retry.** The e-mail changed notice should get BullMQ's next attempt when the `MailSender` fails. That is the stated goal of S2 (`plan.md:109`), but only the welcome's retry is proven (C5). The notice uses the same `OutboxEffectRunner` and sender, so the risk is low, but no test exercises `notifications.send_email_changed_notice` under a rejection.
6. **Not covered: the event payload is not type-bound where it is published.**
   - `confirm-email-change.use-case.ts` publishes an untyped object literal, and `EmailChangedPayload` (`src/modules/identity/application/events/identity-event.ts:35-40`) is not attached to it.
   - The same is true of `identity.account.registered` today, since `AccountRegisteredEvent` is used only in `identity-event.ts` and `public.ts`.
   - If the publisher and the exported type drift apart, the code still compiles. Only C7's runtime assertion would catch it.
7. **Docs: the plan misattributes the secret rule.** `plan.md:178` credits ADR-013 with "the rule of never putting a secret in an event". ADR-013 has no such rule; the new `docs/adr/014-send-e-mail-from-a-notifications-module-behind-a-shared-port.md:21` states it. Neither new payload carries a token: `identity-event.ts:35-40`, and the effects at `schedule-welcome-email.use-case.ts:22` and `schedule-email-changed-notice.use-case.ts:22-26`.
