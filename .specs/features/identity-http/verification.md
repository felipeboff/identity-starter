## Findings

No precision gap, level gap or coverage gap fails a check. These observations are ranked from most to least significant. None of them changes a Result:

1. **C7 checks the exact 401 body for only one refusal cause.** The test uses a revoked session (`identity.routes.spec.ts:157`). The other ten causes reach the edge only as `status 401` (missing header, C8) or are asserted below the edge (C3-C6). This is acceptable because all eleven causes throw the same descriptor, `new AppError(IdentityError.InvalidAccessToken)` (`authenticate.use-case.ts:21`, `:29`, `:34`, `:41`; `authenticate.middleware.ts:28`), and the error mapper is keyed on that descriptor. A future cause that threw a different error would only be caught at the edge by C8, and only for the no-header case.
2. **C13 checks the empty user-agent case on sign-in only** (`auth.routes.spec.ts:167`). Sign-up, oauth and refresh use the same `toSessionOrigin` mapper (`sign-up-with-email.handler.ts:27`, `sign-in-with-oauth.handler.ts:26`, `refresh-session.handler.ts:23`), so checking one flow is acceptable.
3. **C33 compares middlewares with `toEqual([deps.authenticate])`** (`identity.routes.spec.ts:120`). That is a structural comparison, not a reference or class check, so a different middleware object with the same shape would also pass. `toStrictEqual`, or `toBe` on each element, would make it exact. Low impact: there is only one middleware in the module today.
4. **C8 and C17 assert the status only** (`401`) and not the error `code`, and C32 asserts violations loosely (at least one with a string `field`). Each matches the value its check defines, so none of these is a precision gap.
