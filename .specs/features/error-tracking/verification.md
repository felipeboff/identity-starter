- **C8, assembly and "never initialized"** (verified in round 2): the only production assembly is
  `src/main.ts:6` -> `start`. It initializes Sentry only behind `env.SENTRY_DSN === undefined ?
undefined : SentryErrorReporter.create(...)` (`start.ts:51-58`), before `database.connect()`

  `start` describe (`start.e2e.spec.ts:178`), so the baseline client is the one in place before
  any Sentry test in that file.

  pattern (`config.ts:23`) would refuse it. The `.env.example` sample
  (`http://<project-key>@localhost:8000/1`, `.env.example:16`, commented out) matches the pattern.

  asserted on `stop()` itself (`start.e2e.spec.ts:207-210`), and this run took 2 136 ms. Nothing

- **C3, level** (carried from round 1, citations re-read): the proof sits at `HttpErrorMapper`.
  The reporter call is wrapped in `ignoringFailure` (`http-error-mapper.ts:62-75`), and
  `ExpressAdapter.answerError` sends `map()`'s return value (`express-adapter.ts:119-120`), a
  forwarding that C1 crosses over HTTP (`create-server.e2e.spec.ts:124-126`).
- **C5, sensitivity** (carried from round 1): the assertions cover the whole raw envelope and
  require exactly 1 event. The Handoff records that a mutant collecting everything through
  `dataCollection` survived. With `enableRuntimeChannelInjection: false`
  (`sentry-error-reporter.ts:36`), Sentry attaches no request data, so no test observes Landing
