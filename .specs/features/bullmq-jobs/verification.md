## Findings

None of these makes a check fail: each check's claim, as written, has a located assertion that settles it. They are ranked by how much behaviour they leave unproven.

1. **The plan's S1 independent test is only partly proven (C14, sampling).** C14 calls itself the "S1 independent test". The plan (`plan.md:101-102`) defines that test with a mailer that fails once and then works, so the effect gets `processedAt` only after a second attempt, and the `outbox` queue ends empty.
   - `src/app/start.e2e.spec.ts:435-480` uses no failing mailer.
   - The fail-then-succeed path is proven only through the runner called by hand, outside BullMQ (`src/modules/identity/identity.module.integration.spec.ts:274-289`).
   - The queue side is proven only up to "delayed with `attemptsMade` 1" (C8, `bull-outbox-worker.integration.spec.ts:92-94`).
   - No test shows the delayed BullMQ job being picked up again and ending in `processedAt`.
2. **C17 is less precise than its claim.** `bull-scheduled-jobs.integration.spec.ts:133-134` proves at most one run per wall-clock second and at least 2 runs in 3.2 s. If an occurrence is missed (2 runs out of 3), the test still passes. "Once per occurrence" is therefore proven as "never twice", not as "exactly once".
3. **C13 does not prove that the relay is stopped.** `start.e2e.spec.ts:512` sorts a spy that was never called as `(first ?? 0)`, which puts it first. If `stop` never called `OutboxRelay.stop`, "relay" would still sort first, and `:514-521` would still pass. The other five steps cannot hide this way, because an uncalled one would jump ahead of "relay". The relay leg rests on another test, "starts the outbox relay after listening and stops it before closing the database": `start.e2e.spec.ts:548` - `expect(closesWhenRelayStopped).toBe(0)`. That test passed in B4 but is not C13's named proof.
4. **C9 may be flaky.** `bull-outbox-worker.integration.spec.ts:139` reads `queue.getJob` right after `failedAt` appears in the store (`:136-138`), and the read is not wrapped in `waitFor`. The runner writes `failedAt` before BullMQ moves and removes the job, so this read can race. A lost race fails the test; it cannot make it pass falsely. C10 wraps the same read in `waitFor` (`:160-162`).
5. **C14's empty-queue assertion could pass vacuously.** `start.e2e.spec.ts:478-479` (every outbox job count is 0) would also pass if the app's outbox queue used another prefix. It means something only because `start.ts:136-141` gives the same settings, with `prefix: env.APP_NAME`, to both queues, and C19 (`start.e2e.spec.ts:494`) works on the scheduled queue under that prefix.
6. **C7's no-handler case leaves values loose.** `outbox-effect-runner.spec.ts:192` checks the result with `toMatchObject({ outcome: OutboxRunOutcome.ABANDONED })`, and `:199` accepts any `lastError` (`expect.any(String)`). The refused-payload case pins both values. The plan does not fix the no-handler `lastError`, so this is precision, not a contradiction.
7. **C19 covers AC 10 only by reading the assembly (level).** `IdentityModule.scheduledJobs` is `[]` (`identity.module.ts:234`), so at startup level the e2e can only prove removal (AC 11). Creating or updating a scheduler for a declared job (AC 10) is proven at integration level by C15. At startup it rests on reading `start.ts:155` and `:159`. Nothing more is possible until a module declares a job.
8. **C20's "at once" is not timed.** `bull-outbox-queue.integration.spec.ts:103-105` asserts the rejection itself, with the ioredis message produced by `enableOfflineQueue: false` (`src/shared/infrastructure/redis/redis-connection.ts:23`). The only limit on how long it takes is Vitest's default 5 s test timeout; `vitest.config.ts` sets none. It took 117 ms in this run.
9. **Plan values with no check (seen while reading; `light` does not recompute coverage).**
   - Door 2's worker `concurrency: 5` (also in the plan's Impact) is set at `src/shared/infrastructure/jobs/bull-outbox-worker.ts:11` and `:29`. `rg -n -i concurrency src/ --glob '*.spec.ts'` returns no hits.
   - Door 3's template `removeOnComplete: true, removeOnFail: 100` is set at `src/shared/infrastructure/jobs/bull-scheduled-jobs.ts:53-54`. C15 asserts only `attempts` and `backoff`.
   - Door 3's dispatch `Inbound { input: {}, metadata: {}, ip: "", actor: undefined }` is at `bull-scheduled-jobs.ts:82-85`, and no assertion covers it.
   - Door 5 says queues and workers are created after `listen`. That order is visible at `start.ts:123-159`, but no test asserts it.
10. **The `Handoff` section of checks.md is out of date.** `checks.md:109` still lists slice S3, `:111` says "C1-C33 closed", and `:112` cites "Landing door 8, C33". `:114` explains the scope reduction, but those three lines still describe the old 33-check set.
